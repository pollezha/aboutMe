# Реализация задачи

Одна задача за раз. Аргумент — id задачи (например `T2`) или несколько независимых (`T2 T4`); без аргумента —
первая невыполненная задача, у которой выполнены зависимости.

## Режим по умолчанию: оркестратор + implementer
Основная сессия — оркестратор: держит маленький контекст (планы, отчёты, git), код пишет сабагент
`implementer` (свежий контекст, модель из его определения). Так контекст оркестратора не раздувается логами
и исходниками.

1. **Подготовка.** Прочитай задачу в плане и её зависимости. Если задача неясна или противоречит плану/спеке —
   спроси пользователя до запуска. Код и большие файлы оркестратор не читает.
2. **Поручение.** Запусти `implementer` (Agent, `subagent_type: implementer`) с промптом: путь к плану, id задачи,
   решения пользователя и уточнения, которых нет в файлах. Независимые задачи (план помечает их параллельными)
   запускай одновременно, каждую с `isolation: "worktree"`, чтобы не мешали друг другу. Worktree может
   отставать от main — первым шагом агента: `git merge --ff-only main`.
3. **Приёмка отчёта.** `DONE` — дальше; `BLOCKED` или вопрос — реши сам, если ответ есть в плане/спеке/ADR,
   иначе спроси пользователя; затем продолжи того же агента (SendMessage), а не начинай заново.
4. **Независимая проверка.** Не верь отчёту на слово: `git status` / `git diff --stat`, затем быстрые проверки
   затронутой части с хвостами вывода (команды в CLAUDE.md). Читай дифф выборочно — только подозрительные места.
   Для задачи из worktree — смёрджи ветку worktree в текущую и проверь уже здесь.
5. **Коммит.** Conventional Commits: `feat(scope): …`, `fix(scope): …`. Одна задача — один коммит, только файлы
   задачи. Уроки из отчёта — в `docs/learnings.md` тем же коммитом.
6. **Отметка.** `[x]` у задачи в плане. Коротко сообщи: что сделано, какие тесты добавлены, что дальше.

**Сам, без сабагента**, оркестратор делает только мелочи (опечатка, однострочный фикс, правка документа или
конфига) и то, что требует доступа, которого нет у сабагента.

## Цикл исполнителя (его выполняет `implementer`, или оркестратор для мелочей)
1. **Красный.** Тест на поведение из критерия «готово». Запусти — он падает по ожидаемой причине.
2. **Зелёный.** Минимальный код, чтобы тест прошёл. Не трогай то, что не относится к задаче.
3. **Рефакторинг.** Убери дублирование, улучши имена. Тесты зелёные.
4. **Полный прогон.** Сборка + все тесты + линтер. Чинить свои поломки, а не отключать тесты.
5. **Самопроверка диффа** (`git diff`):
   - нет отладочного кода, закомментированных блоков, TODO без задачи;
   - нет секретов и захардкоженных адресов;
   - обработаны ошибки и граничные случаи из спеки;
   - изменения в публичных контрактах есть в ADR.

## Стоп-сигналы
- Тот же тест падает после 3 попыток исправления → `/debug`, не перебирать варианты вслепую.
- Задача оказалась вдвое больше ожидаемого → предложи разбить её в плане.
- Нужна новая зависимость или смена контракта → спроси пользователя.
