# Проектирование и ADR

Результат: короткий design-раздел в спеке (или `docs/design/<feature>.md`) + по одному ADR в `docs/adr/NNNN-<slug>.md` на каждое значимое решение (шаблон `docs/adr/0000-template.md`).

## Шаги

1. **Вход.** Прочитай одобренную спеку, CLAUDE.md, существующие ADR. Если спеки нет — сначала `/spec`.
2. **Драйверы.** Выпиши 3–5 архитектурных драйверов: требования к нагрузке, надёжности, консистентности, безопасности, стоимости, а также ограничения (бесплатные тарифы, один разработчик, сроки).
3. **Модель.** Опиши:
   - компоненты и их ответственность (одно предложение на каждый);
   - потоки данных: синхронные вызовы vs события, кто владелец данных;
   - контракты: эндпоинты / схемы событий / таблицы — только существенное;
   - диаграмма в Mermaid (C4 container или sequence), если компонентов больше трёх.
4. **Варианты.** Для каждого значимого решения — минимум 2 варианта с трейдоффами. Обязательно рассмотри самый простой вариант (монолит, одна БД, без брокера) и явно скажи, почему его недостаточно — или выбери его.
5. **Сквозные вопросы** — пройди чек-лист, отметь «n/a» где неприменимо:
   - идемпотентность и повторная доставка; транзакционные границы (outbox?);
   - ошибки внешних систем: таймауты, ретраи, circuit breaker;
   - аутентификация/авторизация, хранение секретов;
   - наблюдаемость: логи с correlation id, метрики, health checks;
   - миграции и обратная совместимость контрактов;
   - стоимость инфраструктуры.
6. **ADR.** Оформи решения. Одно решение — один ADR. Укажи сигнал для пересмотра.
7. **Ревью дизайна.** Запусти сабагента `reviewer` с задачей «найди слабые места дизайна: единые точки отказа, нарушение границ, лишнюю сложность». Учти обоснованные замечания.
8. **Одобрение** пользователя → статус ADR `accepted` → `/plan`.

## Принципы
- YAGNI: сложность только под реальный драйвер. Для пет-проекта «показать навык» — валидный драйвер, но назови его явно.
- Обратимые решения принимай быстро, необратимые (схема данных, публичный контракт) — тщательно.
