# ADR-0004: Контент — JSON в репозитории со схемой; content-api и вшитый снимок

Статус: accepted · Дата: 2026-10-20

## Контекст
Тексты глав, навыки, ссылки, даты на EN/RU меняет только владелец (сценарий 4). Сайт должен работать без
бэкенда (NFR4, AC10) и не публиковать заглушки (FR9, AC7). Дизайн будет меняться — контент нельзя держать
в разметке.

## Рассмотренные варианты
| Вариант | Плюсы | Минусы | Стоимость изменения потом |
|---|---|---|---|
| A. Тексты в компонентах / i18n-строках | Проще всего | Смешан с дизайном; нет схемы и проверки | Высокая |
| B. Headless CMS (Strapi, Directus) | Админка | Ещё один сервис и БД; владелец один и умеет git | Средняя |
| C. `/content/{en,ru}.json` + JSON Schema; сборка вшивает снимок; content-api отдаёт тот же JSON из PostgreSQL | Одна правда в git, валидация в CI, работает без API; content-api показывает EF Core + кэш + ETag | content-api по сути кэш над файлом — оправдан только драйвером «показать навык» | Низкая |

## Решение
C. Источник правды — JSON в git; схема и валидатор общие для сборки фронта и для content-api. Фронт
сначала рендерит снимок, затем при доступном API подменяет данные, только если монотонная `contentVersion`
(время коммита контента) в API строго больше, — откат бэкенда не возвращает посетителям старый текст.
Стаж в навыках хранится датами работ и вычисляется.

## Последствия
- Становится проще: правка текста = PR; AC7 проверяется в CI; сайт жив без бэкенда.
- Становится сложнее: две копии (снимок и БД) — синхронизируются хэшем версии.
- Сигнал пересмотреть: появится второй редактор контента или нужна правка без деплоя → CMS.
