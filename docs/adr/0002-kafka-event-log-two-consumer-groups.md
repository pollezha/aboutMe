# ADR-0002: Kafka как журнал событий, два независимых потребителя

Статус: accepted · Дата: 2026-10-20

## Контекст
Каждое действие посетителя (FR12) нужно и сохранить в агрегаты (projector → PostgreSQL), и сразу показать
живым (live-hub → SignalR). Нагрузка — сотни событий в день, т. е. брокер не нужен по объёму. Драйвер —
показать навык событийной архитектуры (спека G4) и независимость потребителей (NFR4: падение одного не
ломает другого), плюс возможность пересчитать агрегаты с нуля.

## Рассмотренные варианты
| Вариант | Плюсы | Минусы | Стоимость изменения потом |
|---|---|---|---|
| A. events-api пишет прямо в PostgreSQL, live-hub читает БД | Минимум частей, ~0 ОЗУ сверху | Нет журнала и replay; потребители связаны через БД; не показывает навык | Низкая |
| B. PostgreSQL LISTEN/NOTIFY или таблица-очередь | Одна БД, есть push | NOTIFY не хранит историю; самодельная очередь — изобретение велосипеда | Средняя |
| C. RabbitMQ | Лёгкий, знакомая модель | Очередь, а не журнал: нет replay и независимых офсетов без ухищрений | Средняя |
| D. Kafka (KRaft, 1 брокер), топик `site.events.v1`, группы `projector` и `live-hub` | Журнал с retention и replay, независимые офсеты, партиционирование по ключу, отраслевой стандарт | ≈ 1 ГБ ОЗУ, операционная сложность, нет встроенного OTel в Confluent.Kafka | Высокая (контракт журнала) |

## Решение
D: журнал Kafka с двумя consumer group — единственный вариант, где оба потребителя полностью независимы и
агрегаты можно пересчитать из истории; память укладывается в бюджет VPS (design §8).
JSON-схемы в проекте `Contracts`, без Schema Registry: один продюсер и два потребителя в одном репозитории.

## Последствия
- Становится проще: добавить третьего потребителя без изменения продюсера; пересчёт агрегатов.
- Становится сложнее: идемпотентность (eventId + `processed_events`), проброс трейса через заголовки,
  мониторинг consumer lag, Testcontainers в тестах.
- Запасной путь по сроку: projector и live-hub в одном процессе с двумя группами — контракт журнала не меняется,
  но NFR4 ослабляется. Минимум изоляции: два BackgroundService, `BackgroundServiceExceptionBehavior.Ignore` и
  перезапуск цикла каждого консьюмера; если выбран этот путь — поправить NFR4 в спеке.
- Сигнал пересмотреть: Kafka не влезает в память (T10) → Redpanda (совместима по протоколу) или вариант A;
  появится второй продюсер из другого репо → Schema Registry.
