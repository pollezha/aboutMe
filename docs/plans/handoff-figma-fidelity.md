## Что произошло (прочитай, чтобы не повторить)
Два разрыва подряд, оба нашёл пользователь, а не процесс:
1. **Концепт → Figma.** Figma не повторяет последний концепт пользователя. Агент заменил 8 тематических окон одним
   безликим каркасом, убрал два шрифта, дирижабль с CV, самолёт Telegram, биллборды, бутылку «Write me a message»,
   грузовик на панели маршрута; своего макета острова в Figma нет (вставлена картинка сцены). Основание — разбор
   концепта D1–D25, написанный агентом **по версии v5**, тогда как пользователь в v6 сознательно сделал «themed windows ·
   server room»; пункты разбора не выносились пользователю на решение. Полная таблица:
   `docs/design/concept-vs-figma.md`.
2. **Figma → сайт.** 3D-остров ушёл на прод простыми коробками, расстановка глав и пины не как в макете, мелочи
   первого экрана расходятся. Задачи принимались по тестам и бюджетам, кадры с макетом не сравнивались.
   Разбор: последний раздел `docs/learnings.md`.

## Шаг 0. Решения пользователя (до любой правки)
Задай одним AskUserQuestion и запиши ответы в `docs/design/concept-vs-figma.md`, раздел «Решения»:
1. Окна: вернуть тематические окна v6 как есть (лицензия, накладная со штрихкодом и треком, строительная лента,
   тёмный ЦОД с объёмными стойками, диплом с печатью, Contact с крупным заголовком) или общий каркас **с фирменным
   элементом каждой главы**?
2. Шрифты: вернуть Barlow Condensed (TimePath) и Fraunces (Education)? Бюджет шрифтов ≤ 150 КБ, занято 114 КБ.
3. Первый экран: дирижабль с CV, самолёт Telegram, биллборды GitHub/Email, бутылка, грузовик на линии маршрута —
   вернуть рядом с карточкой Hero, вместо неё или частично?
4. Остров: эталон — сцена из v6 как есть (без The Lab), или пользователь хочет её поменять? И путь для сайта:
   доводить 3D-сцену до вида v6 (рекомендуется) или временно картинка сцены с HTML-пинами.
5. Мобильная версия и 768/1280 (в v6 их нет): адаптировать новый вид по тем же принципам, что сейчас в Figma, или
   пользователь хочет посмотреть варианты?
Если ответ «посмотреть варианты» — сделай 2–3 варианта кадрами в Figma на странице 🧪 и снова спроси.

## Фаза A. Figma по концепту
Скилы: `figma-use` (обязательно перед `use_figma`), `figma-generate-design`, `figma-generate-library`. Сохраняй
структуру файла (Cover, Getting started, Foundations, Components, Windows, Screens, Specs, Concept), связи стилей и
переменных, text styles для всех текстов, ledger `docs/design/figma-state.json` после каждого изменения.
1. **Foundations.** Шрифты и text styles по решению 2; токены цветов: тематические окна (тёмный ЦОД, кремовый диплом,
   жёлтая лента) — семантическими переменными с режимами Day/Evening/Night, контраст ≥ 4,5:1 (таблица контрастов
   на странице Foundations).
2. **Components.** Компоненты, которых не хватает: дирижабль, самолёт, биллборд, бутылка, грузовик на маршруте,
   двухстрочный пин острова (кружок с номером в цвете главы, название, подпись), фирменные элементы окон (штрихкод,
   трек статусов, стойка ЦОД, печать, машиночитаемая строка лицензии).
3. **Windows.** По одной задаче на окно: 01 Profile, 02 ProSpace, 03 TimePath, 04 Tech stack, 05 Education, 06 Contact,
   07 Summary, 08 Monitoring — desktop и mobile; контент сохраняется из текущих окон (он уже в `content/en.json`).
4. **Screens.** Первый экран 1440, 1280, 768, 390 в Day/Evening/Night и RU; остров — эталонный кадр сцены без The Lab
   и без мусорных подписей.
5. **Specs.** Обновить страницу Specs и `figma-brief.md` под новые решения.

Приёмка каждой задачи фазы A: пара «кадр v6 ↔ кадр Figma» (для новых размеров — «Figma ↔ принципы v6») в
`docs/design/compare/A-<task>/`, сверка по чек-листу `visual-acceptance.md`, `design-reviewer`, затем **кадр
пользователю**. Окно или экран без его «да» не считается готовым. После фазы A — повторный экспорт токенов в
`frontend/scripts/design/figma-tokens.json` и `npm run gen:theme` (CI ловит дрейф).

## Фаза B. Сайт по Figma
`/plan` → `docs/plans/stage-3c-figma-fidelity.md` по правилам нарезки: задача = один компонент, одно окно, одно здание,
один пин, одна правка первого экрана; у каждой — узлы Figma, фреймы × состояния для приёмки, файл спеки модуля
`docs/spec/frontend/<module>.md`, тест. Визуальные вехи пользователю минимум после: первого тематического окна,
расстановки острова, первого здания, пинов, первого экрана целиком. Покажи план списком, получи одобрение, затем
`/implement` по задаче.

Приёмка каждой задачи фазы B — процедура `visual-acceptance.md`: эталонные кадры Figma снимаешь ты и отдаёшь
исполнителю; исполнитель кладёт пары `docs/design/compare/<task>/<frame>.{figma,site}.png`, обновляет спеку модуля;
ты сам открываешь каждую пару и запускаешь `design-reviewer`; расхождение в рамках задачи — доработка тем же агентом,
вне задачи — вопрос пользователю. Плюс `bash scripts/check.sh frontend` и `npm run test:e2e` зелёные; бюджеты не
ломать (main ≤ 150 КБ gzip, сцена ≤ 2 МБ, шрифты ≤ 150 КБ, `scene_ready` < 4 с — `npm run build` печатает size-limit).

## Рабочие правила
- Прод: <https://aboutme.polezhaev-yasha.workers.dev> — деплоится сам на каждый push в `main` (Cloudflare Workers Builds,
  `frontend/wrangler.jsonc`). После каждой вехи проверь прод теми же кадрами.
- В том же рабочем каталоге работают бэкенд-сессия (`services/`, `src/`, `tests/`) и agent-dx. Их файлы не трогай; общие
  (`CLAUDE.md`, `.claude/settings.json`, `frontend/package.json`) — после сообщения им (`ListAgents` / `SendMessage`).
- Ветки worktree сливай `git merge --no-edit`, затем `git status --short | grep '^UU'`; поверх конфликта не коммить.
  `.github/workflows/` правит только пользователь. Новые зависимости — только с согласия пользователя.
- Замечания исполнителей о внешнем виде — вопрос пользователю, а не «не блокер». Ничего не добавлять и не убирать
  сверх эталона и задачи.
