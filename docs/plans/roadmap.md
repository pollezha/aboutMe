# Дорожная карта: сайт-портфолио MVP

Спека: docs/spec/portfolio-mvp.md · Дизайн: docs/concept/design-review.md · Исходник: docs/concept/plan.md
Дата: 2026-10-20 · Оценка: ≈ 16 рабочих дней (8 этапов, 0–7)

Это верхнеуровневый план. Перед стартом каждого этапа его задачи детализируются через `/plan`
в `docs/plans/<этап>.md` (атомарные задачи с тестом и критерием «готово»); ADR — через `/architecture`.

## 1. Цели и метрики

| # | Цель | Метрика | Цель MVP | Чем меряем | Где проверяется |
|---|---|---|---|---|---|
| G1 | Понятно за 30 секунд | Имя, роль, статус, Contact, CV видны без кликов | 100% при 1280×720 и 390×844 | Playwright-скриншоты | Этап 3, 7 |
| G2 | Быстро открывается | LCP; время до интерактивной 3D | < 2,5 с; < 4 с | Lighthouse CI, Web Vitals из events | Этап 3 (CI), 7 (прод) |
| G3 | Доступность и качество | Lighthouse Perf / A11y; axe | ≥ 85 / ≥ 95; 0 нарушений | Lighthouse CI, @axe-core/playwright | Этап 3, 7 |
| G4 | Сайт = доказательство навыков | Живые сервисы; сквозной трейс | 5/5 сервисов healthy; трейс браузер → SignalR | `/health`, Tempo | Этап 4, 5, 6 |
| G5 | Надёжность | Uptime 30 дней | ≥ 99,5% | Внешний пинг (UptimeRobot) | Этап 6 → +30 дней |
| G6 | Открытый чистый код | Запуск одной командой; CI; тесты | Да; зелёный; тесты в каждом сервисе | Чистый клон + README; GitHub Actions | Каждый этап, итог — 7 |
| G7 | Конверсия в контакт | Доля визитов с `cta_click` | Базовая линия за 1-й месяц, затем цель | projector → дашборд | Этап 7 → +30 дней |

Вспомогательные метрики процесса: доля задач, закрытых с выводом `/verify` (100%); раундов `/review`
на этап (≤ 3); повторяющиеся уроки в learnings.md закреплены тестом/линтером.

## 2. Как проверяем (общий ритуал)

**После каждой задачи** (`/implement`): тест сначала → код → локальные тесты → коммит (Conventional Commits).

**После каждого этапа — шлюз (stage gate).** Этап закрыт, только если пройдены все пункты:
1. `/verify` — чистая сборка, все тесты, линтеры, запуск, проверка AC этапа; отчёт `VERIFY: PASS`
   с выводом команд прикладывается к PR.
2. `/review` — ревью диффа этапа по REVIEW.md, ≤ 3 раунда, 0 blocker / 0 major.
3. Проверки этапа из таблицы «Шлюз» ниже (метрики с числами, не «выглядит нормально»).
4. Демо пользователю: что работает, скриншоты/ссылка, отклонения от плана.
5. `/learn` — уроки в docs/learnings.md, правки CLAUDE.md / REVIEW.md, если были.
6. PR в main, тег `v0.<этап>.0`, отметка в чек-листе раздела 5.

Если шлюз не пройден — этап не закрывается, следующий не начинается (кроме задач, явно помеченных
как параллельные). Сдвиг срока фиксируется в разделе 6.

### Этап 4 — Сервисы · 4 дня
**Цель:** сайт работает на собственном бэкенде; каждое действие — событие в Kafka.
- E4-T0 Spike (≤ 0,5 дня): Kafka KRaft + Testcontainers + проброс trace context в заголовках — риск в начало.
- E4-T1 Contracts: событие `site.events.v1` (eventId UUIDv7, type, occurredAt, sessionId, lang, theme,
  payload), DTO контента; версия схемы.
- E4-T2 gateway (YARP): маршруты, rate limit, CORS, фильтр ботов.
- E4-T3 content-api: EF Core + PostgreSQL, сид из JSON, output cache + ETag; миграции отдельной задачей.
- E4-T4 events-api: валидация, обезличивание (хэш sessionId с суточной солью), producer с идемпотентностью.
- E4-T5 projector: consumer group A → агрегаты в PostgreSQL, идемпотентность по eventId.
- E4-T6 live-hub: consumer group B → SignalR (онлайн, лента агрегатов).
- E4-T7 Фронт: content из API со вшитым снимком как fallback; отправка событий; SignalR-клиент.
- E4-T7b Записка в бутылке (FR17): `POST /api/messages` в events-api → Telegram Bot API, honeypot, лимит
  3/ч в gateway, форма на фронте — TC-21.
- E4-T8 Интеграционные тесты (Testcontainers) на каждый сервис и сквозной сценарий.
- Запасной вариант по сроку: projector и live-hub в одном процессе с двумя consumer group (ADR).

| Шлюз этапа 4 | Как проверить |
|---|---|
| Все сервисы в AppHost healthy | дашборд Aspire / `curl /health` × 5 |
| AC8 (часть данных): повторная доставка не дублирует агрегат | интеграционный тест |
| AC9: счётчик обновился ≤ 2 с | Playwright с двумя вкладками |
| AC10: content-api остановлен → сайт работает на снимке | ручной сценарий + Playwright |
| Негатив: невалидное событие → 400, флуд → 429 | `curl` |

- E5-T5 Окно Monitoring: путь клика по реальным 5 сервисам, ссылка на репозиторий сайта и пример трейса
  (скриншот), без публичной Grafana.
- Подключить плагин grafana-mcp (см. scripts/install-plugins.sh).

## 6. Отличия от docs/concept/plan.md и почему
- **Добавлен этап 0** — открытые вопросы и `[ADD]` блокируют контент окон; без CV главная CTA ведёт в `#`.
- **Добавлен этап 2 (дизайн)** — концепт сделан под один холст 1440×900; мобильный и 1280 нельзя
  оставлять на «полировку», иначе сцену и окна переделывать дважды.
- **Мобильный/2D-режим и Lighthouse CI перенесены в этап 3** из 6-го — метрики G1–G3 проверяются с первого
  релиза, а не в конце.
- **Статический деплой фронта в этапе 3** — в plan.md сказано «после 5-го дня сайт можно показывать»,
  но деплой стоял пятым этапом; теперь показываемый URL есть сразу после сайта без бэкенда.
- **Spike Kafka/трейсинга в начале этапа 4** — самый рискованный кусок по правилу «неизвестное — вперёд».
- **The Lab исключён из MVP** и с карты (в plan.md он уже вне MVP, но в макете есть на карте).
- Срок: ≈ 16 дней вместо 14 за счёт этапов 0 и 2; этап 2 можно вести параллельно с 1.

## 7. Риски и откат
| Риск | Признак | Действие |
|---|---|---|
| 5 сервисов + мониторинг не влезают | этап 4 > 5 дней | объединить projector и live-hub; мониторинг — Grafana Cloud free |
| 3D тормозит | Perf < 85 или 3D > 4 с | агрессивнее InstancedMesh, меньше декора, 2D по умолчанию на мобильных |
| Kafka/мониторинг не влезают в 8 ГБ | `docker stats` > 7 ГБ | heap Kafka, лимиты, вынос телеметрии в Grafana Cloud |
| Спам событиями | рост 429/ошибок в events-api | rate limit, фильтр ботов, валидация схемы |
| Контент не готов к этапу 3 | `[ADD]` в JSON | убрать пункт из окна, а не публиковать заглушку |
| Плохой релиз | красный smoke | CD откатывает на предыдущий тег |
