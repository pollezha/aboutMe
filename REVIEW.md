# REVIEW.md — что важно при ревью этого репозитория

> По мотивам практики команды Claude Code (Anthropic): коротко, конкретно,
> с доказательствами. Держи файл до ~60 строк.

## Что считается провалом здесь
- Двойной подсчёт или потеря события: projector/live-hub не идемпотентны по `eventId` (повторная доставка Kafka).
- Неверный результат бизнес-расчёта без ошибки (тихий баг).
- Строка из публичного API без закрытого списка или белого списка символов; ошибка обработчика, которая останавливает консьюмер навсегда (нет разделения poison / транзиентная).
- Утечка секретов / PII в логи, события, ответы API, репозиторий: IP — только в памяти лимитера (в логах маска /24), `sessionId` — только хэш с суточной солью.
- `/alive` зависит от сети или зависимостей (БД, Kafka) — проверки без тега `live` в `/alive` недопустимы; `/health` наружу не публикуется.
- Заглушки в контенте (`content/*.json`): lorem, TODO, пустые ссылки — рекрутер видит их первым.
- Превышение бюджетов фронта (size-limit, Lighthouse CI, axe) или поломка 2D-fallback без WebGL.
- Нарушение обратной совместимости контракта (API, схема события, миграция).
- Документация/README, которые врут о поведении.
- Расхождение с Figma в рамках задачи: элемент потерян, добавлен сверх макета, не тот цвет/текст/стиль/место
  (процедура и чек-лист — `docs/design/visual-acceptance.md`); UI-задача без пары кадров Figma ↔ сайт.

## Обязательно проверить
- Корректность: граничные случаи, null, пустые коллекции, конкурентный доступ, повторная доставка.
- Ошибки: нет проглоченных исключений; внешний вызов → таймаут + понятная ошибка.
- Безопасность: валидация входа, авторизация на каждом эндпоинте, параметризованные запросы.
- Данные: миграции обратимы; нет N+1; индексы под новые запросы.
- Тесты: новое поведение покрыто; тест падает без фикса.
- Визуальная приёмка: для UI-изменений есть `docs/design/compare/<task>/`, обновлена спека модуля `docs/spec/frontend/`.
- Соответствие CLAUDE.md; если изменение делает строку в CLAUDE.md устаревшей — отметить.

## Пропускать
- Сгенерированный код, lock-файлы, миграции-снапшоты: `frontend/package-lock.json`, `services/*/Infrastructure/Persistence/Migrations/*.Designer.cs`, `services/*/Infrastructure/Persistence/Migrations/*ModelSnapshot.cs`, `bin/`, `obj/`, `frontend/dist/`
- Чистое форматирование (это работа форматтера).

## Формат находок
- Каждая находка: `severity | файл:строка | что не так | почему это проблема | как исправить`.
- Severity: **blocker** (баг/безопасность/потеря данных) · **major** (вероятный баг, отсутствие теста на важное) · **minor** (читаемость, упрощение).
- Без файла и строки — не находка, а догадка. Догадки не публиковать.
- major/blocker только при достижимом сценарии сбоя на текущем коде и конфигурации; «станет проблемой на этапе N» — это minor с пометкой этапа или задача в план.
- Не больше 3 minor-замечаний (nits) за ревью.
- Сводка начинается с числа: «2 blocker, 1 major, 0 minor». Если чинить нечего — так и написать.

## Сходимость
- Максимум 3 раунда ревью на одно изменение. После 3-го — пересмотреть подход, а не латать.
- Со 2-го раунда смотреть только новый дифф.
- Не повторять замечание, которое уже было отклонено с объяснением.
